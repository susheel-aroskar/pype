I’m a principal engineer implementing an idea I have long held in my head, as a take home project.

I’m going to implement “pype” - a push-pull based load balancing solution that replaces the traditional reverse proxy based load-balancers.  It acts as a central rendezvous point. Instead of clients sending requests to a traditional reverse proxy + load balancer that then directly load-balances them across multiple backend service instances while clients block waiting for the responses, in pype both the clients and the backend service instances connect to a pype instance and,
	- clients push (POST) their requests to in-memory queues designated for individual services,
    - service instances pull (GET) client requests intended for them from these queues,
	- service instances process these requests, then push (POST) responses back to the individual clients' transient in-memory queues,
    - clients can then pull (GET) responses intended for them from their own private queues when they are ready to consume them.

By reversing the role (push vs pull), pype makes many of the complex problems inherent in load balancing requests across dynamic pool of service instances trivially solvable - for example, service discovery, optimal load balancing, back-pressure, auto-scaling, rate limiting etc.

We are going to build both the pype server and a pype client to achieve this. Let's start by building the server first. pype server is an async, FastAPI based Python REST server that exposes few REST API endpoints.

# pype internally maintains in memory queues for both backend services and clients. These are maintained using two registries - a client_registry and a service_registry, both of which are singleton objects for a given pype FastAPI app.
    - Service queues are stored against a {service_name} (string) in a service_registry. Service name is common to all service instances of a given service. Service queues are long lived. Once created, they continue to exist till the pype instance is shutdown.
    - client queues are stored in client_registry against their individual `client_id`s as read from their JWT token. Each `client_id` is a 256-bit URL-safe random string generated by the server at auth time, and serves a dual purpose: it identifies the client AND acts as the client's capability — knowing the id is what proves authority over the client's queue (since it is cryptographically unguessable, there is no separate secret). Client queues are **lazy-created**: `POST /auth/client` does NOT pre-register an entry. Instead, the entry is created on first use of `/clients/{client_id}` — by either a service POSTing a response or the client itself GETting one. This makes Pype clustering-friendly: a client's JWT can land on any pype instance behind a load balancer and that instance simply spins up a fresh queue on demand. Client queues are transient and have to account for cleanup if a client doesn't log off cleanly, so each entry stores the last time the client was "seen" and the reaper evicts stale ones after an inactivity threshold.
    - Both service and client queues are async queues and have max size limits specified when they are created. These limits are read from a FastAPI configuration settings following the normal best practices such that there are default values configured in code but a user can easily override them using config file or environment variables. client queue default size should be 8, named services queues default size should be 8000.

# Payload format and Content-Type
- Payloads (both client requests and service responses) are opaque to pype. They may be text or binary; internally pype stores them as `bytes`. Pype itself never parses the payload.
- Callers (clients and services) pass the payload's media type using the standard HTTP `Content-Type` request header on POST.
- If `Content-Type` is absent on an inbound POST, pype defaults it to `application/json`.
- Pype preserves the inbound `Content-Type` end-to-end:
    - On `POST /services/{service_name}`, the inbound `Content-Type` is captured into `PypeRequest.content_type` along with the payload bytes, and returned as the `Content-Type` HTTP response header on the corresponding `GET /services/{service_name}`.
    - Same flow on the response side: `POST /clients/{client_id}` captures `Content-Type` into `PypeResponse.content_type`, and `GET /clients/{client_id}` returns it as the `Content-Type` HTTP response header.

# Sticky-routing support: the X-Pype-Server-IP header
- On every successful auth (`POST /auth/service` and `POST /auth/client`), the server sets a `X-Pype-Server-IP` HTTP response header carrying its own RFC 1918 private IPv4 address (10.x.x.x, 172.16-31.x.x, or 192.168.x.x). If no qualifying private address is detectable, the value is `127.0.0.1`.
- The IP is auto-detected at server startup and cached for the process lifetime; it can be overridden via the `PYPE_SERVER_INTERNAL_IP` env var or the `internal_ip` setting.
- Clients (both pype-client `ServiceConnection` and `ClientConnection`) capture this header and echo it back as `X-Pype-Server-IP` on every subsequent request.
- The server itself does not currently validate or act on the inbound header — it exists purely to enable a future reverse proxy / load balancer in front of pype to do **sticky routing**: send a given client's traffic back to the exact pype instance that holds that client's queue in memory. Without stickiness, a multi-instance pype deployment would split a client's session across nodes and fail (the client's queue is on instance A but the response goes to instance B's empty registry).

# REST endpoint /auth/service: 
## POST:
- Service instances POST to this endpoint with their credentials to authenticate themselves. For this prototype, we will assume any {service_name} is a valid credential. The authentication will always succeed.
- The JWT issued by the server contains these claims:
    - `role`: "service" (hardcoded string)
    - `name`: caller-provided service_name, string
    - `service_secret`: server-generated secure random unique id for the service, string. For future use — the server does not validate it on subsequent requests in this prototype.
- The auth response is `Content-Type: application/json` with the following shape:
```json
{
  "access_token": "<jwt>",
  "token_type": "Bearer",
  "role": "service",
  "name": "<service_name>",
  "service_secret": "<server-generated>"
}
```
- The `access_token` is the JWT, used as `Authorization: Bearer <jwt>` on every subsequent request.
- The other fields mirror the JWT claims so the service does not need to decode the JWT to read its own identity.
- Multiple instances of the same service can authenticate using the same service_name.
- A successful auth will register an async queue inside the service_registry against the {service_name}, if one is not already registered. {service_name}s are NOT predetermPlined and are registered dynamically with services_registry whenever `/auth/service` is invoked and succeeds with a new service name.

# REST endpoint /auth/client:
## POST:
- Clients POST to this endpoint with their credentials to authenticate themselves. For this prototype, any client name is a valid credential. The authentication will always succeed.
- The JWT issued by the server contains these claims:
    - `role`: "client" (hardcoded string)
    - `name`: client-provided name, string. Carried only for debugging/observability; not used for authorization.
    - `client_id`: server-generated 256-bit URL-safe random string. Doubles as the client's capability — knowing the id is what proves authority over the client's queue. There is no separate `client_secret`.
- The auth response is `Content-Type: application/json` with the following shape:
```json
{
  "access_token": "<jwt>",
  "token_type": "Bearer",
  "role": "client",
  "name": "<caller-provided>",
  "client_id": "<256-bit URL-safe random string>"
}
```
- The `access_token` is the JWT, used as `Authorization: Bearer <jwt>` on every subsequent request.
- The `client_id` field mirrors the JWT claim so the client does not need to decode the JWT to read its own id.
- This endpoint does **not** pre-register a queue. The client's queue is lazy-created on first use of `/clients/{client_id}` (either a service POSTing a response or the client GETting one). This keeps the auth path stateless and lets the client's JWT subsequently land on any pype instance behind a load balancer.
## DELETE:
- Clients do DELETE to this endpoint to log off.
- Verify that a valid JWT token with `role = "client"` exists, otherwise return UNAUTHENTICATED if no valid JWT, 400 USER ERROR if the role doesn't match.
- The JWT signature alone is sufficient authority to remove this client's own queue: the JWT's `client_id` claim was issued by us, signed by us, and points at exactly one client entry. We remove the queue from the clients_registry, idempotently (no-op if it's already gone — reaped or previously deleted).


# REST endpoint /services/{service_name}: 
## POST:
- clients POST requests to this endpoint to send the requests to a service identified by {service_name}. 
- POST must verify that a valid JWT token with role = "client" exists for the request, otherwise return UNAUTHENTICATED if no valid JWT, 400 USER ERROR if the role doesn't match. The JWT signature is the sole authority — the `client_id` is a server-signed 256-bit random string and entry presence in the registry is bookkeeping, not auth. If no entry exists yet for this client_id (e.g., the client just authenticated and is sending its first request), it is lazy-created.
- The POST request contains,
    - client_id: string, from the JWT token (also acts as the capability)
    - request_id: string, supplied as a request parameter. It is unique per calling client. Calling client is responsible for maintaining the uniqueness.
    - content_type: string, from the standard `Content-Type` HTTP request header. Defaults to `application/json` if absent.
    - payload: POST request body as raw bytes. No format restriction. This allows client to POST any type of request body including binary payload.
- Server wraps these details in a PypeRequest dataclass with fields (client_id, request_id, content_type, payload) and puts the PypeRequest in the queue for the {service_name} in the service_registry. 
- If the queue for the {service_name} does not already exist in the registey, one is created and registered against {service_name} on the fly.
- POST updates the `last_seen` time of the client's queue (a successful authenticated POST from the client proves liveness).
- Returns the status `202 Accepted` if successful.

### Optional `block` query parameter (synchronous request/response in one call)

POST also accepts an optional boolean query parameter `block` (default false). When `block=1` (or `block=true`), the server, after successfully enqueueing the PypeRequest onto the service queue, **turns around within the same HTTP request and dequeues from the originating client's response queue** before returning. This lets a client perform a request/response round-trip in a single HTTP call when latency is tight and parallelism is not needed.

Behavior with `block=1`:

1. Both phases (enqueue onto service queue, dequeue from client queue) share **one deadline** computed as `now + timeout` so the user-supplied `timeout` is honored end-to-end. As soon as phase 1 (enqueue) completes, the remaining ms is recomputed and used as the budget for phase 2 (dequeue).

2. Phase 2 is the **same** dequeue logic that powers `GET /clients/{client_id}` — it is **not** filtered by `request_id`. The server returns whichever response is at the head of the client's queue, with `X-Pype-Request-Id` correctly identifying which request the response actually corresponds to. The client library is responsible for noticing if the returned `request_id` does not match the one it just POSTed and falling back to `GET /clients/{client_id}` to find its actual answer.

Response codes when `block=1`:

| Status | Meaning | Body |
|---|---|---|
| `200 OK` | A response was dequeued from the client's queue. | response payload + `Content-Type` + `X-Pype-Request-Id` headers |
| `202 Accepted` | Request enqueued onto the service queue, but no response landed in the client's queue within the deadline. | empty |
| `503 Service Unavailable` | Service queue stayed full for the whole timeout; request was **not** enqueued. | empty |
| `400` / `401` / `403` | as for the non-blocking POST | error JSON |

When `block` is absent or false the existing behavior is unchanged: 202 on success, 503 on full queue.
## GET:
- Services do GET to this endpoint with their own {service_name} to dequeue the messages intended for them. 
- GET must verify that a valid JWT token with role = "service" exists for a request, and the name from the JWT token matches {service_name} otherise return UNAUTHENTICATED response if no valid JWT, 400 USER ERROR if the role doesn't match.
- If authentication passes get the service queue from the service_registry using {service_name} and dequeue a message from the queue to return to the service.
- One GET call dequeues and returns one PypeRequest, even when multiple messages are waiting in the same queue. The original request POST body is returned as a response body for the GET. The accompanying `client_id` and `request_id` are returned as HTTP response headers (`X-Pype-Client-Id`, `X-Pype-Request-Id`). The stored `content_type` is returned as the standard `Content-Type` response header. This design imposes no restrictions on the actual request body flowing from clients to services and eliminates any need to parse the request body inside the pype server for maximum throughput.
- If the queue for the {service_name} does not already exist, one is created and registered in services_registery dynamically.


Both GET and POST are blocking calls with a int query parameter "timeout" (0 <= timeout <= server defined max) determining how long the caller will block:
    - timeout parameter completely missing (None) -> blocks till server determined max value specified in the config settings, defaults to 8 minutes (480000 ms)
    - timeout = 0 -> do not block, return immediately if the queue is full for POST or empty for GET
    - any other value for timeout in (0, server_max] -> block for that many milliseconds
    - timeout < 0 or timeout > server_max -> reject with 400 Bad Request, body indicating the allowed range

If the POST times out because {service_name} queue has reached it's max capacity, return 503 Service Unavailable. The backend service doing POST drops the response on the floor on 503.

If the GET times out because {service_name} queue is empty, return 204 No Content


# REST endpoint /clients/{client_id}: 
## POST:
- Services POST do this endpoint to return a response to a particular request (identified by the request_id) from a partcular client (identified by the client_id). 
- POST must verify that a valid JWT token with role = "service" exists for the request, otherwise return UNAUTHENTICATED if no valid JWT, 400 USER ERROR if the role doesn't match.
- The capability check on the target client is implicit: `client_id` is a 256-bit random string, so a service that didn't legitimately pull this client's request can't know the id and can't address this endpoint at all. The server lazy-creates the client's entry if missing — this lets a service successfully respond even if the originating client's queue lives on a different pype instance in a clustered deployment, or has been reaped between request and response.
- POST contains,
    - client_id: string, from path parameter
    - request_id: string, from query parameter
    - content_type: string, from the standard `Content-Type` HTTP request header. Defaults to `application/json` if absent.
    - payload: The request body contains the response to be returned to the client, raw bytes.
- Server wraps `request_id`, `content_type` and `payload` in a PypeResponse dataclass with fields (request_id, content_type, payload). `client_id` is not stored in PypeResponse — the queue is already keyed by client_id.
- Client's queue is looked up from clients_registry using {client_id} (lazy-created if missing). The PypeResponse is enqueued.
- POST does NOT update the last_seen time of the queue belonging to this client - identified by {client_id} - in the client_registry.
- Returns the status `202 Accepted` if successful.     
## GET:
- Clients do a GET to this endpoint to retrieve responses for the requests they have submitted to various services. 
- GET must verify that,
    - a valid JWT token exists, otherwise return 401 Unauthorized.
    - the JWT's role is "client", otherwise return 400 Bad Request.
    - the {client_id} path parameter matches the `client_id` claim in the JWT, otherwise return 403 Forbidden.
- The JWT signature is the sole authority — registry entry presence is not checked. If no entry exists yet for this client_id (e.g., the client is polling before any service has POSTed a response, or it just bounced over from another pype instance behind a load balancer), it is lazy-created with an empty queue and the GET long-polls on it.
- client's queue is retrieved from the client_registry using {client_id}. If the queue is not empty, the first PypeResponse is dequeued and returned to the client. The `request_id` is returned as the `X-Pype-Request-Id` HTTP response header, the `content_type` as the standard `Content-Type` response header, and the `payload` as the response body.
- A client can NOT ask for a response to a specific request. Instead, if the client has submitted multiple requests and one or more responses for those requests are available in the client's queue, the first one of them will be returned. The responses may be returned out of order with respect to the original requests. That's OK, the pype client we are going to build will know how to deal with this.
- If the queue for a {client_id} doesn't exist the client gets a 400 USER ERROR response back.
- GET updates the last_seen time of the queue belonging to this client - identified by {client_id} - in the client_registry to now. The update happens whether or not a response is dequeued (i.e., even on a 204 No Content), because the GET itself proves liveness.

Both GET and POST are blocking calls with a int query parameter "timeout" (0 <= timeout <= server defined max) determining how long the caller will block:
    - timeout parameter completely missing -> blocks till server determined max value specified in the config settings, defaults to 8 minutes (480000 ms)
    - timeout = 0 -> do not block, return immediately if the queue is full for POST or empty for GET
    - any other value for timeout in (0, server_max] -> block for that many milliseconds
    - timeout < 0 or timeout > server_max -> reject with 400 Bad Request, body indicating the allowed range

If the POST times out because {client_id} queue has reached it's max capacity, return 503 Service Unavailable.
If the GET times out because {client_id} queue is empty return 204 No Content.



# REST endpoint /load/services
## GET:
- This endpoint can be used by autoscaling agents to analyze load on backend services fronted by pype. It returns the current length of queue stored against each {service_name} in services_registry as an array of objects. Queue length is a great surrogate metric for the load on that service. Example response:
```
    [
        {"service_name": <service_name_1>, "load:" <queue1_length>}, 
        {"service_name": <service_name_2>, "load:" <queue2_length>}, 
        ...
    ]
```
- This endpoint needs no Auth (JWT token etc.)


# Background task: client queue reaper

Client queues are transient. If a client never calls DELETE on `/auth/client`, its queue and entry in `client_registry` would leak forever. A background reaper task periodically evicts client queues whose `last_seen` is older than a configured inactivity threshold.

## Configuration (in `app/config.py`)
- `client_reaper_period_seconds: int = 60` — how often the reaper runs.
- `client_reaper_batch_size: int = 1000` — **minimum** number of `client_registry` entries the reaper examines per tick. Floor; the actual batch scales up with registry size (see below).
- `client_reaper_target_sweep_seconds: int = 600` — target wall-clock latency for one full sweep regardless of registry size. The per-tick batch is `max(batch_size, ceil(registry_size / (target_sweep_seconds / period_seconds)))`. Small registries do at most `batch_size` per tick; very large registries scale up so abandoned entries don't sit around for hours. Default 600s = 10 min, matching the inactivity threshold so stale entries are caught within roughly one threshold window.
- `client_inactivity_threshold_seconds: int = 600` — entries with `now - last_seen > threshold` are evicted. Default 10 minutes; this is comfortably larger than the 8-minute max blocking-GET timeout, so a client doing a long blocking GET that times out and immediately retries will not be reaped between calls.

## Lifecycle
- The reaper is started in the FastAPI lifespan context (`@asynccontextmanager` registered on the app), as a single long-lived `anyio` task spawned at startup. It is cancelled cleanly on shutdown.
- It is not a request handler and has no auth.

## Algorithm (correctness over speed; bounded work per tick)
The reaper must NOT iterate over `client_registry.keys()` directly while the dict may be mutated by request handlers (would risk `RuntimeError: dictionary changed size during iteration`). It must also bound its work per tick so a million-queue registry doesn't monopolize the event loop.

State carried across ticks (held on the reaper itself, not in the registry):
- `cursor: list[int]` — a snapshot of `client_registry` keys taken at the start of a sweep.
- `cursor_idx: int` — index into `cursor` of the next key to examine.

Per tick:
1. If `cursor` is empty or `cursor_idx >= len(cursor)`, take a fresh snapshot: `cursor = list(client_registry.keys())`, `cursor_idx = 0`. (Snapshotting `keys()` into a list is an atomic O(n) copy under the GIL — safe even if other coroutines mutate the dict afterwards.)
2. Examine up to `client_reaper_batch_size` keys starting at `cursor_idx`:
    - For each `client_id`, look up the entry with `client_registry.get(client_id)`. If it's gone (already DELETEd or reaped earlier), skip.
    - If `now - entry.last_seen > client_inactivity_threshold_seconds`, evict: remove from `client_registry`. Closing the queue is not required (no consumers/producers left for an abandoned client; GC will collect).
    - Increment `cursor_idx`.
3. Sleep `client_reaper_period_seconds` and loop.

This way each tick is bounded, the reaper resumes from where it left off across ticks, and snapshot-based iteration is immune to concurrent mutation.

## Notes
- Eviction is best-effort. A request handler racing the reaper for the same `client_id` may observe a missing entry; in the lazy-create model that's harmless — the handler simply re-creates a fresh queue and proceeds. Reaped responses sitting in queues are dropped.
- The reaper never touches `service_registry` — service queues are intentionally long-lived.
